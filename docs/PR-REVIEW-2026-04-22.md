## PR #10 — `data-action="new-session"` on NewSessionItem

**Verdict: DO-NOT-MERGE**

**What it does:** Adds `data-action="new-session"` to one `<A>` element at `packages/app/src/pages/layout/sidebar-items.tsx:292`.

**Findings:**

1. **Multi-render ambiguity (Codex, high).** `NewSessionItem` is rendered from `WorkspaceSessionList` per workspace at `sidebar-workspace.tsx:246-252`, and `showNew` is true for every empty workspace + on all touch devices at `sidebar-workspace.tsx:326`. The sidebar renders a `SortableWorkspace` for each workspace at `layout.tsx:2409-2418`, so the live DOM can contain N nodes with `[data-action="new-session"]`. Any E2E locator keyed on this attribute alone is ambiguous by construction.
2. **Cross-PR collision.** PR #23 independently adds the same literal string to `titlebar.tsx:273-285`. If both land, `[data-action="new-session"]` matches elements in two different surfaces with different visibility/disabled rules — exactly the flake the attribute was meant to eliminate. There is no uniqueness registry or CI check.
3. **Attribute is already overloaded.** `data-action` is used for runtime event delegation (`prompt-input.tsx:1374`) and on non-interactive wrapper divs (`settings-general.tsx:238-260`). The attribute name is not a purely-test-only convention in this codebase.

**Remediation path:**
- Rename to `sidebar-new-session` (surface-scoped).
- Move to `data-testid` if the intent is test-only, leaving `data-action` for app semantics.
- Build a typed selector registry in `packages/app/src/testing/` with a uniqueness lint and a CI check that fails when two files register the same id.
- Coordinate with PR #23 before landing either.

## PR #12 — `data-action="session-sidebar-archive"` on archive button

**Verdict: MERGE-WITH-CHANGES**

**What it does:** Adds `data-action="session-sidebar-archive"` to one hover `IconButton` at `sidebar-items.tsx:249-255`.

**Findings:**

1. **Accessibility contract weakening (Codex, medium).** This icon-only button already has `aria-label={language.t("common.archive")}`. Playwright's `getByRole('button', { name: /Archive/ })` with a pinned test locale is a real alternative and is ALSO the accessibility-required selector. Adding `data-action` creates a parallel, product-decoupled contract that can stay green even after an accessibility regression removes/renames the label. Destructive actions are the worst place to weaken the accessible-name contract.
2. **Location in the name.** `session-sidebar-archive` bakes the current surface (sidebar) into the selector. A future refactor moving archive into a context menu breaks E2E for an implementation-only reason. Prefer `session-archive`.
3. **Shared `Tooltip` renders portal content, not `title`.** Any plan to fall back to `getByTitle` is invalid — verified in `packages/ui/src/components/tooltip.tsx`.

**Remediation path:**
- If the PR must land, rename to `session-archive` (behavior-oriented, surface-agnostic).
- Prefer Playwright `getByRole('button', { name: /Archive/ })` with locale pinning.
- Merge only after PR #10's registry-or-rename strategy is settled, so these two PRs converge on one selector pattern.

## PR #13 — 404 for nonexistent permission/question/session IDs

**Verdict: DO-NOT-MERGE**

**What it does:** Adds pre-checks via `list().some(...)` in three route handlers at `packages/opencode/src/server/instance/{permission,question,session}.ts` so they return 404 for missing IDs. Also bumps `MessageID.zod.optional() → MessageID.zod` on the diff endpoint's input schema at `server/instance/session.ts:486`.

**Findings:**

1. **`session.diff` is a pure API contract break with no backend implementation behind it (Codex, high).**
   - Schema at `server/instance/session.ts:486` is switched from optional to required.
   - Service at `packages/opencode/src/session/summary.ts:134-145` still accepts `messageID?: MessageID` and **never references `messageID` in the body** — it only reads `["session_diff", input.sessionID]` from storage. Confirmed by direct read of summary.ts.
   - `SessionSummary.DiffInput` at `summary.ts:161-164` still exposes `messageID: MessageID.zod.optional()`.
   - Generated JS SDK at `packages/sdk/js/src/v2/gen/sdk.gen.ts:2063-2069` and `types.gen.ts:3663-3672` still has `messageID?`.
   - In-tree caller in the TUI at `packages/opencode/src/cli/cmd/tui/context/sync.tsx:490-495` calls `client.session.diff({ sessionID })` with no messageID. Will now 400.
   - A contract change with no implementation, no SDK regen, and existing callers that violate it is not a bugfix — it is a gun pointed at deployed clients.

2. **TOCTOU races are still possible and pre-checks belong in the service layer (Codex, high).** The new pattern is `list()` → `.some()` → mutate. The service at `packages/opencode/src/permission/index.ts:203-206` silently returns on missing, and `221-257` shows that a successful reply eagerly removes sibling pending requests in the same session. A concurrent reply/reject can pass the pre-check, lose the race, and still return 200 with a dropped decision. The pattern also collapses "already resolved" into "not found" — callers cannot distinguish stale retry from bogus ID, so no path to 409 exists. The repo already has centralized `NamedError` → HTTP mapping at `packages/opencode/src/server/middleware.ts:20-27`, so the check belongs in the service as a `NotFoundError`/`ConflictError` throw, not as a route-level probe.

**Remediation path:**
- **Revert** the `MessageID.zod` change at `server/instance/session.ts:486`. If message-scoped diffs are a goal, implement them end-to-end in `Summary.diff`, regenerate `packages/sdk/js`, update in-tree callers, bump the SDK version, and ship as a separate API change PR.
- Move the not-found/already-resolved detection into `Permission.Service.reply`, `Question.Service.reply/reject`, and `SessionRevert.Service.revert`. Let each throw `NotFoundError` or `ConflictError`. The existing `server/middleware.ts:20-27` already maps these to 404/409.
- Add `packages/opencode/test/server/*-httpapi.test.ts` coverage for: 404 on bogus ID, 404 on deleted-after-list, 409 on already-resolved. Harness at `test/server/question-httpapi.test.ts` is copy-pasteable.

## PR #14 — PATCH /config persistence + round-trip + logging

**Verdict: DO-NOT-MERGE**

**What it does:** Three changes across `packages/opencode/src/config/config.ts` and `packages/opencode/src/server/instance/config.ts`:
- `globalConfigFile()` at `config.ts:1087-1094` gains an `OPENCODE_CONFIG_DIR` preference.
- `update` adds `Effect.tapError` logging and `updateGlobal` swaps `next = parseConfig(updated, file) → next = config`, reorders write-before-assign, and changes `invalidate() → invalidate(true)`.
- PATCH `/config` route at `server/instance/config.ts:57-64` calls `cfg.updateGlobal(globalFields)` instead of `cfg.update(config)` and strips `command`/`agent` from the payload.

**Findings:**

1. **Instance-scoped route now mutates global state (Codex + deep review, high).** `/config` is registered on the instance router. The SDK exposes it with `directory`/`workspace` query params. A dedicated `/global/config` already exists at `server/instance/global.ts:159-183`. Repointing `/config` to `updateGlobal` duplicates semantics, silently breaks the per-directory contract, and means a call scoped to one workspace can mutate a global file shared across workspaces.
2. **Write/read asymmetry on `OPENCODE_CONFIG_DIR` (Codex, high).** Confirmed by direct read of `loadGlobal` at `config.ts:1239-1263`:
   ```
   pipe({},
     mergeDeep(yield* loadFile(path.join(Global.Path.config, "config.json"))),
     mergeDeep(yield* loadFile(path.join(Global.Path.config, "opencode.json"))),
     mergeDeep(yield* loadFile(path.join(Global.Path.config, "opencode.jsonc"))),
   )
   ```
   `loadGlobal` reads ONLY from `Global.Path.config`. PR #14 makes `globalConfigFile()` prefer `OPENCODE_CONFIG_DIR`, so write goes to `$OPENCODE_CONFIG_DIR/opencode.json` while `getGlobal` continues reading `~/.config/opencode/*`. The UI flow `global.config.update().then(bootstrap).get()` returns success then repopulates from stale state.
3. **Silent discard of `command` and `agent` with false 200 (Codex, medium).** The handler strips both keys, writes the rest, then `return c.json(config)` — echoing the full input including the dropped fields. Callers see 200 and the shape they submitted while the file on disk is different.
4. **JSONC `{file:…}` justification is unsubstantiated.** The PR body claims `command`/`agent` templates contain `{file:…}` references that `patchJsonc` misreads. Grep of real `~/.gpd/opencode.json` and `~/.config/gpd/opencode.json` returns zero `{file:` occurrences. `paths.ts:77-129` shows `{file:…}` runs at load, not at patch. `patchJsonc` uses `jsonc-parser.modify`/`applyEdits`, which preserve comments.

**Remediation path:**
- **Revert** the PATCH `/config` route change. Keep `/config` workspace-local via `cfg.update`. Use `/global/config` for global writes.
- **Split into three PRs:**
  - (a) ~4-line landable: `invalidate() → invalidate(true)` at `config.ts:1637` + `Effect.tapError` logging in `update` at `config.ts:1597-1599`.
  - (b) Separate design discussion: promote `OPENCODE_CONFIG_DIR` to a first-class global tier in `loadGlobal`/`getGlobal` so read and write agree. Or scrap `OPENCODE_CONFIG_CONTENT` in favor of a single config source (see PR #22).
  - (c) Drop the `command`/`agent` strip entirely. If those fields are invalid in this route, reject with 4xx — do not echo them back silently.
- **Do not accept** the `next = config` change. Keep `next = parseConfig(updated, file)` so the response body reflects on-disk truth.
- Add regression tests: remote-workspace `/config` writes; `/global/config` PATCH→GET round-trip with `OPENCODE_CONFIG_DIR` set; `command`/`agent` persistence.

## PR #15 — Sidecar watchdog, force-kill, stable-env respawn

**Verdict: DO-NOT-MERGE**

**What it does:** Adds a 500 ms polling watchdog + force-kill on exit + "stable-env" respawn across `packages/desktop/src-tauri/src/{lib.rs,cli.rs}`.

**Findings:**

1. **Respawned sidecar comes up with creds the frontend never learns (Codex + deep review, high).** `SidecarReady` at `lib.rs:75` is a `oneshot::Receiver<ServerReadyData>` wrapped in `Shared`. `ready_tx.send(...)` fires once at initial spawn at `lib.rs:643-648`. The frontend consumes this once via `createResource` at `packages/desktop/src/index.tsx:469`, and that value is frozen into `ServerConnection`. The watchdog loop in the PR (diff `lib.rs:616-654`) generates `new_port = get_sidecar_port()` (re-binds `127.0.0.1:0` → new port guaranteed unless `OPENCODE_PORT` is set) and `new_password = uuid::Uuid::new_v4()`, but emits no Tauri event and cannot re-fire the consumed oneshot. Frontend hits dead port → `ECONNREFUSED` or 401 permanently. "Respawn" in the PR title is a misnomer — recovery is cosmetic.
2. **Shutdown race can spawn an orphan after app exit (Codex + deep review, high).** Lifecycle state is split across an `AtomicBool` (`stopping`) and a shared `Mutex<Option<Child>>`. The watchdog polls `stopping` first, then independently inspects the child. `kill_sidecar` flips `stopping=true` and `take()`s the child. If those two operations interleave between the watchdog's two reads, the watchdog sees `None`, treats it as unexpected death, and respawns — after shutdown was already committed. `RunEvent::Exit` doesn't wait for the watchdog to terminate, so the new process survives the Tokio runtime shutting down → orphan sidecar on the user's machine.
3. **Unbounded restart storm, no health gating (Codex + deep review, medium).** Loop sleeps 500 ms, respawns immediately on any death, no backoff, no max retries. A sidecar that crashes at startup (DB lock, port clash, `OPENCODE_CONFIG_CONTENT` parse panic) is respawned forever. Diff binds the post-respawn health check join handle to `_hc` and drops it — no liveness observation after first spawn. Log line "Sidecar respawned successfully" fires before the new process has accepted any traffic.
4. **SIGKILL-first exit creates a predictable log-loss window (Codex + deep review, medium).** `force_kill_sync` at `cli.rs:87-95` unconditionally sends SIGKILL. The GPD logger at `packages/opencode/src/sink/gpd-logger.ts:169-175` debounces flushes by 1 s. Finalizer at `:230-239` only clears in-memory state. Ordinary quit = up to 1 second of `message_updated`/`part_updated` events lost per active session. Compounds with TOS-decline flow (`quit_app → app.exit(0) → RunEvent::Exit` → force-kill) which is a common user path.
5. **Architectural: supervisor design is wrong.** Poll + flag + mutex + oneshot scattered across functions cannot be made correct without a race somewhere. The Tokio idiom here is one supervisor task that owns the `Child`, the endpoint credentials, health state, and a shutdown signal (`JoinHandle` + `CancellationToken`). The current PR layers a watchdog on top of the existing spawn logic without consolidating ownership.

**Remediation path:**
- Rearchitect. Single supervisor `tokio::spawn`ed task that owns `Child`, `ServerReadyData`, and receives an explicit shutdown `CancellationToken`. `kill_sidecar` cancels the token, awaits the task, returns.
- Publish new `ServerReadyData` on every respawn via a Tauri event + frontend listener that rebinds `ServerConnection`. Alternative: keep port+password stable (persist originals, reuse them, check that the old port is re-bindable).
- Add `consecutive_failures` counter, exponential backoff (1s → 2s → 4s → 8s, cap at 60s), bounded retry budget (e.g. 5 failures in 60s = fatal). Surface fatal state as a Tauri event and a user-visible UI.
- Send SIGTERM first with a ~1 s deadline, then SIGKILL. Add a scope finalizer to `gpd-logger` that drains pending events before the scope closes.
- Split out the `/System/Library/CoreServices/{app}.app` addition at diff `lib.rs:217` — unrelated to the PR title.
- Replace `.unwrap()`/`.expect()` on `Mutex::lock` (diff L626, L645) with `.ok()` or `PoisonError::into_inner` so a watchdog panic doesn't cascade into a poisoned lock at shutdown.

## PR #16 — chmod 600 on login profile after writing API key

**Verdict: DO-NOT-MERGE**

**What it does:** Adds a single `chmod 600 "$GPD_KEY_EXPORT_FILE" 2>/dev/null || true` line at `install-gpd/install:1190` (post-patch), after the write at the "no rc file matched" fallback path.

**Findings:**

1. **Default POSIX export is the real problem (Codex, high).** The POSIX installer writes the key to three places: `~/.gpd/config/litellm.env` (consumed by the `gpd` wrapper), `~/.local/share/opencode/auth.json` (consumed by app+CLI, chmod 600), and a login-profile export line. The Windows installer deliberately skips the login-profile export with a "zero functional benefit" comment. Every POSIX consumer is already reading from `litellm.env` or `auth.json`. The login-profile export is a redundant third copy whose only additional exposure surface is dotfile syncers, backup tools, and editor plugins — none of which `chmod 600` mitigates on a user-owned file. The fix is to remove the default export, not to tighten perms on an exposure the product does not need.
2. **Chmod attached to the wrong path (Codex + deep review, medium).** The patched site at `install:1190` is the `already_wrote == false` fallback that runs only when no login rc file was matched. The primary paths at `install:1156` and `install:1169` use `write_rc_block` on the actual zsh/bash login rc and have no chmod — these are the paths the majority of installs hit. The PR does nothing for them.
3. **Race window at pre-creation.** `install:1187` runs `[[ -f "$GPD_KEY_EXPORT_FILE" ]] || : > "$GPD_KEY_EXPORT_FILE"` before `write_rc_block` writes the key. The file is created with default umask (644) and `write_rc_block`'s `mktemp`+`mv` pattern preserves the destination's existing perms on `mv`. The chmod-after-write closes the steady-state window but not the pre-creation-to-write window.
4. **`|| true` hides chmod failures.** Silent fallback masks audit-class failures (read-only dir, bind-mounted rc, etc.).

**Remediation path:**
- **Preferred:** remove the default `GPD_KEY_EXPORT_LINE` login-profile export. Match the Windows installer. Keep `litellm.env` (chmod 077 via `umask 077` subshell) and `auth.json` (os.chmod 0o600) as the two canonical stores. Document any POSIX-only consumer before reintroducing the export.
- **If the export must remain:** wrap `write_rc_block` (or a dedicated secret-bearing helper) in `umask 077`. After the `mv`, enforce `chmod 600` and verify the resulting mode. Do not use `|| true` on the chmod — fail loudly. Apply at all three call sites (install:1156, 1169, 1190).
- Add a regression test: drop a known-644 rc file into a temp install root, run the installer, assert the resulting mode is 600 at every secret-bearing site.

## PR #17 — Remove 50 ms timer race in SetupGate waitForPaint

**Verdict: DO-NOT-MERGE**

**What it does:** Rewrites `waitForPaint()` at `packages/app/src/context/global-sync/bootstrap.ts:35` to keep only `requestAnimationFrame(() => setTimeout(resolve, 0))`. Removes the `setTimeout(finish, 50)` fallback that raced rAF. Adds `queueMicrotask`-via-`Promise.resolve().then(resolve)` for non-browser environments. Also wraps `setGlobalStore("ready", true)` in `batch()`.

**Diff verified:** `gh pr diff 17` shows the 50 ms safety timer is explicitly deleted. The SSR fallback only fires when `requestAnimationFrame === undefined`.

**Findings:**

1. **Hidden-window boot stalls indefinitely (Codex, high).** In browsers and Tauri's WebView, `requestAnimationFrame` is suspended while the window is hidden / occluded / backgrounded. `waitForPaint()` gates both:
   - `bootstrapGlobal()` → `setGlobalStore("ready", true)` at `bootstrap.ts:132`. SetupGate (`app.tsx:285`, `:421-436`) blocks on `globalSync.ready`.
   - `bootstrapDirectory()` at `bootstrap.ts:349` → `status="complete"` transition.
   The removed 50 ms timer was the only bound preventing an unbounded paint dependency. With it gone, launching the app into a hidden/backgrounded window leaves: CLI-provisioned `gpd` auth undiscovered, directory stores stuck at `partial`, welcome/loading UI on screen until user brings window to foreground.
2. **Prior reviewer's "split out Rust tests" comment was based on a phantom diff.** Actual PR is one file, `+8/-14`. No Rust tests exist in the diff. Ignore that recommendation.
3. **`batch()` around a single write is a no-op.** Solid's `batch` only matters for multiple writes. Harmless, but the PR body's "per Solid.js best practices" framing is inaccurate.

**Remediation path:**
- Keep the post-paint path for visible documents. Restore the safety escape hatch one of these ways:
  - Race `requestAnimationFrame(() => setTimeout(resolve, 0))` against a timer (same structure as before; raise to 200–500 ms if 50 ms was too aggressive).
  - OR `if (typeof document !== "undefined" && document.visibilityState !== "visible") return resolve()` as a fast path, then rAF for visible docs.
- Add a regression test: monkey-patch `requestAnimationFrame = () => {}` in Happy-DOM or similar, assert `bootstrapGlobal()` still reaches `ready` and `bootstrapDirectory()` still reaches `status="complete"`.
- Drop the `batch()` wrapper unless the intent is to prepare for future multi-write expansion.

## PR #18 — Use session instance directory for DELETE /session SSE routing

**Verdict: DO-NOT-MERGE**

**What it does:** At `packages/opencode/src/server/instance/middleware.ts`, when no `workspaceID` is provided, resolves via `Filesystem.resolve(sessionInfo.directory)` instead of falling back to `process.cwd()`-derived directory. Renames helper `getSessionWorkspace → getSessionInfo`.

**Findings:**

1. **Workspace session creation still mis-routes (Codex, high).** `WorkspaceRouterMiddleware` at `middleware.ts:64-65` derives workspace only from `sessionInfo?.workspaceID || url.searchParams.get("workspace")`. Codex's claim verified at `packages/sdk/js/src/v2/client.ts:17`:
   ```ts
   function rewrite(request: Request, values: { directory?: string; workspace?: string }) {
     if (request.method !== "GET" && request.method !== "HEAD") return request
     ...
   }
   ```
   The SDK's `rewrite` bails early for non-GET/HEAD. Headers (`x-opencode-directory`, `x-opencode-workspace`) are NOT copied to query params for POST/DELETE/PATCH. But the server-side middleware reads ONLY query params for workspace routing. Net: `client.session.create({ workspaceID })` via scoped-workspace mode POST /session runs under the caller's instance, and `Session.create()` persists `directory = InstanceState.directory` for the new session — i.e., the wrong directory is stamped at creation. DELETE later trusts the stamped directory, but creation can still write the wrong value. The PR fixes a symptom.
2. **Orphan-DELETE path drops `session.deleted` SSE (Codex, medium).** At `middleware.ts:82-92`, when `workspaceID` is present but the workspace record is missing, the middleware hits the "weird state" DELETE escape hatch and calls `next()` without an instance. `Session.remove()` explicitly disables publish when no instance is present. Delete succeeds, but the TUI never receives `session.deleted`, so the sidebar and the active session view stay stale until manual refresh.

**Remediation path:**
- Extend `rewrite()` at `packages/sdk/js/src/v2/client.ts:17-42` to also copy `x-opencode-workspace` → `?workspace=` on non-GET/HEAD. OR read the `x-opencode-workspace` header server-side in `WorkspaceRouterMiddleware` and fold it into `workspaceID`.
- For the orphan-DELETE path, pass enough instance context to let `Session.remove()` publish `session.deleted`. Use `sessionInfo.directory` if workspace record is missing. Or emit a compensating `session.deleted` event explicitly after `next()`.
- Add regression tests: `createOpencodeClient({ experimental_workspaceID }).session.create()` stores the workspace-instance directory, not the caller directory; DELETE with missing workspace record still produces an SSE `session.deleted`.
- The DELETE-side fix in this PR is reasonable as a partial; don't merge until the POST-side fix is in the same PR or lands first.

## PR #19 — Auto-register project on `/:dir` URL navigation

**Verdict: DO-NOT-MERGE**

**What it does:** Adds a `createEffect` in `Layout` at `packages/app/src/pages/layout.tsx:580-585` that calls `layout.projects.open(currentDir())` when the URL param points at an unregistered directory.

**Findings:**

1. **Persists dead projects with no rollback (Codex, high).** `layout.projects.open(dir)` fires a session load but does not await it, and writes the project into the persisted `server.projects` store immediately. If the directory is missing / unreadable / permission-denied, the later failure only surfaces as a toast — the broken project remains in the persisted sidebar/recent-projects state forever. A stale bookmark or paste-jacked link materially mutates global state.
2. **Bypasses TCC / locked-folder preflight (Codex, high).** The rest of the app routes through `navigateToProject` → `platform.checkProjectAccessible` → `layout.projects.unlock` for macOS-locked folders (documented at `docs/GPD_DISTRIBUTION.md:471-481`). The new effect calls raw `layout.projects.open(dir)` and skips the entire preflight. On macOS with a TCC-locked folder, direct URL navigation now falls through to a generic session-load failure instead of the dedicated reconnect flow that the sidebar and deep-link paths were explicitly engineered to use.
3. **`rejectUnsafeProjectPath` is a bypassable trust boundary (Codex, high).** Verified by direct read of `packages/app/src/utils/project-path.ts:14-68`:
   ```ts
   const p = path.trim()
   ...
   const n = p.replace(/[\\/]+$/, "")
   if (n === h) return { key: "project.rejection.homeDir" }
   ```
   Pure string comparison. No `realpath`, no `path.resolve`, no symlink follow, no case-fold. `<home>/Documents/..`, alias paths, case-variant `/USERS/...`, URL-encoded `%2e%2e`, and any symlink to a forbidden root all bypass. Before this PR the check was a best-effort UX guard. With URL-driven auto-registration, it becomes a trust boundary — and it doesn't hold up to that role.

**Remediation path:**
- Preflight the candidate path with `platform.checkProjectAccessible` (or an existence/readability check on non-Tauri) before the store write. Only commit `server.projects.open` after the check succeeds.
- Route direct `/:dir` opens through the same `openSafe` / `navigateToProject` helper used elsewhere. Handle `locked` and `missing` statuses explicitly.
- Replace the string comparison in `rejectUnsafeProjectPath` with canonicalization: `await platform.realpath(p)`, normalize separators, case-fold on macOS/Windows, then compare. Add regression tests for `..` segments, symlink aliases, case-variant roots, URL-encoded inputs, and Windows UNC paths.

## PR #20 — Session list row removal on delete + deep-link navigation

**Verdict: DO-NOT-MERGE**

**What it does:** Three changes:
- Adds a trailing-slash fallback to the SSE event listener in `packages/app/src/context/global-sync.tsx:327-347` (linear scan to find the matching child store when directory strings don't match exactly).
- Adds `parseAnySchemeUrl` and `parseSessionDeepLink` in `packages/app/src/pages/layout/deep-links.ts:13-58`.
- Loops over deep links and calls `session.get` then navigates in `packages/app/src/pages/layout.tsx:1460-1467`.

**Findings:**

1. **Trailing-slash fallback masks cache pollution (Codex + deep review, high).** Verified by direct read of `packages/app/src/context/global-sync/child-store.ts:124-166`:
   ```ts
   function ensureChild(directory: string) {
     if (!children[directory]) {
       ...
       vcsCache.set(directory, {...})
       metaCache.set(directory, {...})
       iconCache.set(directory, {...})
       ...
     }
   }
   ```
   All four caches (`children`, `vcsCache`, `metaCache`, `iconCache`) plus `lifecycle`, `pins`, `disposers` are keyed by the raw `directory` string. The SSE-listener fallback only recovers `children.children[directory]` — everything downstream still uses the alias key. A `/repo/` event hitting a `/repo` store:
   - `mark()` writes last-access against the alias → real store's TTL is never refreshed → can be evicted mid-event-processing.
   - `vcsCache.get(alias)` returns nothing → `vcs.branch.updated` stops persisting branch state.
   - `sdkFor(alias)` creates a **leaked duplicate SDK client** under the alias key.
   - `server.instance.disposed` queues `applyDirectoryEvent(alias)` → creates a **second child store** for the trailing-slash variant.
   Root fix is canonicalization at `ensureChild` and everywhere a child-keyed lookup occurs. The linear-scan bandage does not address any of the above.
2. **Scheme allowlist weakened (Codex, medium).** `parseAnySchemeUrl` accepts any `URL`-parseable input as long as `hostname === "session"`. Sibling `parseUrl` at `deep-links.ts:4` still pins to `opencode://`. Tauri schemes registered at `packages/desktop/src-tauri/tauri.conf.json:67` are `["gpd"]`. `https://session/abc` and `file://session/abc` would currently be accepted. Before this PR, the deep-link path had one consistent validation boundary; after, `parseSessionDeepLink` silently weakens it.
3. **Last-response-wins navigation race (Codex, medium).** The loop at `layout.tsx:1460-1467` fires one `session.get` per link and navigates on every completion. Deep links are explicitly batched (`deepLinks` is an array, pending URLs drained together). With fire-and-forget, the final route is whichever request resolves last — not the last URL in the batch, not the user's current navigation. A slow stale lookup yanks the UI back to an older session after a newer deep link or a user action.
4. **No tests.** `packages/app/src/pages/layout/helpers.test.ts` already has `parseDeepLink` coverage — trivially extendable for `parseSessionDeepLink`, `parseAnySchemeUrl`, and `collectSessionDeepLinks`.

**Remediation path:**
- Canonicalize workspace keys at `ensureChild` (and at `sdkFor`, `mark`, `applyDirectoryEvent`, `disposeDirectory`, `pins`). Use a single `workspaceKey(dir: string): string` helper. Have the event-path fallback return the canonical key and use it for every downstream mutation.
- Replace `parseAnySchemeUrl` with one canonical `parseAppSchemeUrl` that allowlists `gpd` and `opencode`. Use it in every deep-link helper.
- Make deep-link handling deterministic: process session links sequentially, OR stamp each batch with a monotonic token and discard stale `session.get` completions, OR resolve only the LAST session link.
- Add test coverage in `helpers.test.ts` for: `/repo` vs `/repo/` event routing (cache-key invariants), `parseSessionDeepLink` accepts `gpd://session/<id>` + rejects `https://session/<id>`, deep-link batch resolution order.

## Cross-cutting Concerns

### 1. Selector registry (affects #10, #12, #23)

Three PRs add `data-action` attributes with no shared registry, no uniqueness check, and inconsistent naming conventions. Collision already demonstrated (#10 × #23). This will get worse with every PR. Recommend:

```ts
// packages/app/src/testing/selectors.ts
export const SELECTORS = {
  SIDEBAR_NEW_SESSION: "sidebar-new-session",
  TITLEBAR_NEW_SESSION: "titlebar-new-session",
  SESSION_ARCHIVE: "session-archive",
  ...
} as const satisfies Record<string, string>

// Uniqueness enforced by string-literal union in type
```

Add a CI check: `grep -ro 'data-action="[^"]*"' packages/app/src | awk -F'"' '{print $2}' | sort | uniq -c | awk '$1>1'` fails build if any value appears on >1 DOM node in the final build.

### 2. Config persistence contract (affects #14, #22)

`OPENCODE_CONFIG_DIR` has inconsistent read/write semantics:
- Loader treats `OPENCODE_CONFIG_DIR` entries as "local" tier (`config.ts:1357,1429`).
- No write path currently targets `$OPENCODE_CONFIG_DIR/opencode.json`.
- `getGlobal` reads only `Global.Path.config/*`.
- `Config.update` writes `${InstanceState.directory}/config.json`.

Neither PR resolves this cleanly. Ship one of:
- **Option A:** Drop `OPENCODE_CONFIG_CONTENT`. Write a real file on first run to `$OPENCODE_CONFIG_DIR/opencode.json`. Let the normal discovery chain load it. User-editable.
- **Option B:** Promote `OPENCODE_CONFIG_DIR` to a first-class global tier in `loadGlobal`. Then `/global/config` PATCH→GET round-trips work.

Pick one, document it in `docs/GPD_DISTRIBUTION.md`, rewrite #14 and #22 against the chosen model.

### 3. Supervisor architecture (affects #15)

The current spawn lifecycle splits `Child`, `stopping`, `ready_tx`, and health across multiple primitives. PR #15 layers a watchdog on top of this structure, and that layering is the problem. The right move is one supervisor task that owns everything and exposes a small API:

```rust
enum SidecarState { Spawning, Ready(ServerReadyData), Degraded(Reason), Fatal(Reason) }
```

With state changes broadcast via a Tauri event the frontend subscribes to for rebinding credentials. This is outside the scope of a bug-fix PR — worth scheduling as a dedicated refactor before reattempting #15.

### 4. Workspace routing (affects #18)

The SDK `rewrite` at `packages/sdk/js/src/v2/client.ts:17` copies `x-opencode-*` headers to query params ONLY for GET/HEAD. The server middleware reads only query params. Every POST/DELETE/PATCH that should be workspace-scoped is actually running under the caller's instance. #18 patches one symptom in DELETE; the real fix is to extend `rewrite` to all HTTP methods OR to make the server read the header.
